You will build a console Task Report that combines users and their tasks from a public testing API.

CieleGoals

  • čítať dokumentáciu cudzieho REST API a zostaviť request;
  • rozlíšiť kolekciu, jeden resource a vnorený endpoint;
  • spájať údaje z endpointov /users a /todos;
  • pracovať s GET, POST, PATCH a DELETE bez zamieňania ich významu;
  • navrhnúť klienta, ktorý má timeout, zrozumiteľné chyby a offline režim.
  • read third-party REST API documentation and construct a request;
  • distinguish a collection, one resource and a nested endpoint;
  • combine data from the /users and /todos endpoints;
  • work with GET, POST, PATCH and DELETE without confusing their meaning;
  • design a client with a timeout, readable errors and an offline mode.

Úloha 6 — Jeden HTTP klient, nie request všadeTask 6 — One HTTP Client, Not Requests Everywhere

Presuňte sieťové operácie za malé rozhranie ApiClient. Všetky requesty musia používať spoločný httpx.Client, base URL, hlavičku User-Agent a explicitný timeout.

Volajúci kód nemá poznať detaily skladania URL ani volať raise_for_status() na viacerých miestach.

Move network operations behind a small ApiClient interface. All requests must share one httpx.Client, base URL, User-Agent and explicit timeout. Calling code should not assemble URLs or repeat raise_for_status().

class ApiClient:
    def get_users(self) -> list[User]: ...
    def get_user_todos(self, user_id: int) -> list[Todo]: ...
    def create_todo(self, user_id: int, title: str) -> Todo: ...

Úloha 7 — Chyby, ktoré majú odlišný významTask 7 — Failures with Different Meanings

Program musí rozlíšiť aspoň tieto situácie:

  • timeout;
  • chybu spojenia alebo DNS;
  • HTTP 404 pre neexistujúci resource;
  • odpoveď, ktorá nie je platný JSON;
  • platný JSON s neočakávanou štruktúrou.

Nepoužívajte holé except. Na overenie 404 použite neexistujúce ID; ostatné scenáre môžete overiť malou lokálnou funkciou alebo upravenou fixture bez poškodenia produkčnej URL.

Distinguish timeout, connection or DNS failure, HTTP 404, invalid JSON and valid JSON with an unexpected structure. Do not use a bare except. Use a missing ID for 404 and controlled local inputs for the remaining cases.

Chyba API: používateľ 9999 neexistuje (HTTP 404).
Chyba siete: služba momentálne nie je dostupná.
Chyba dát: odpoveď nemá očakávanú štruktúru.

Úloha 8 — POST a význam statusu 201Task 8 — POST and the Meaning of Status 201

Pošlite novú úlohu cez POST ako JSON. Názov musí byť po strip() neprázdny a userId musí patriť existujúcemu používateľovi.

  • overte status 201 Created;
  • spracujte vrátený objekt ako Todo;
  • následným GET overte, či resource naozaj zostal uložený;
  • do reportu jasne napíšte zistenie o perzistencii testovacieho API.

POST a new task as JSON. Validate its title and user first, expect 201 Created, parse the returned object and use a later GET to determine whether the testing API actually persists the resource.

payload = {

Úloha 9 — PATCH, DELETE a pozorovanie kontraktuTask 9 — PATCH, DELETE and Contract Observation

Na existujúcom todo vykonajte dve samostatné operácie:

  • PATCH, ktorý mení iba completed;
  • DELETE toho istého resource.

Predpokladaný status si najprv zapíšte podľa dokumentácie, až potom spustite request. Porovnajte request body, response body a následný GET. Vysvetlite rozdiel medzi úspešnou HTTP odpoveďou a trvalou zmenou dát.

PATCH an existing todo by changing only completed, then DELETE it. Predict the statuses from the documentation before running the requests. Compare request body, response body and a later GET, then explain the difference between an HTTP success and persistent state.
